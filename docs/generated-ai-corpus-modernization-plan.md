## Shared Template Structure

The generator contains:

- hardcoded paper data
- `pageHead()`
- `shell()`
- `renderPaper()`
- `renderHub()`
- `renderCite()`
- card/link helpers
- citation helpers
- reference helpers

The current data and template live in one file. There is no separate JSON input.

## Current Visual Mismatch

The rendered pages in the repo have newer metadata, attribution blocks, CSS version, and shell elements than the full generator currently emits.

During Phase 5, a full generator run rewrote all 12 generated outputs and would have removed current metadata/shell material. Those outputs were restored. A narrow `--hub-only` mode was added to update only the AI Governance hub section without rewriting every generated page.

## Current Navigation Behavior

The full generator emits older research-archive navigation, not the shared Phase 1 shell.

## Editorial Cleanup Risks

- Editing rendered generated pages directly can be lost if the full generator is rerun.
- Editing only the generator can unintentionally rewrite all generated output.
- Hard-ban cleanup in generated pages must happen in source data or templates.
- Attribution and route-status notes must be generated or protected before regeneration.
- PCPI is referenced by the generator but is not generated by it.

## Where Changes Belong

Generator templates:

- shared shell markup
- metadata
- canonical links
- footer
- route-status blocks
- repeated callouts
- CSS version
- JSON-LD structure

Source data:

- paper abstracts
- subtitles
- section text
- related links
- citation text
- download links

Rendered HTML:

- only temporary inspection or emergency repair
- not durable source for generated paper bodies

## Preserving Historical Copy

Before any modernization pass:

1. Save a route-by-route generated baseline.
2. Confirm which public wording is historical and should remain.
3. Avoid rewriting long bodies during shell modernization.
4. Review generated diffs page by page.
5. Keep PCPI separate because it is not generated by this script.

## Route-Status Notices

Route-status notices should be added through generator helpers, not manual HTML patches.

Possible notices:

- corpus status
- paper status
- generated-page source notice
- archive/current status where needed

Do not add status labels that imply a paper is outdated unless the author approves that classification.

## Shared Shell Markers

Shared-shell markers should be introduced later only after the generator template is modernized.

Recommended approach:

- add marker-rendering support to `shell()`
- add generated pages to `scripts/apply-shared-shell.mjs` in a small batch
- run the generator
- run shared shell
- verify deterministic output

Do not add all 12 pages to the shared-shell target list until diffs are easy to inspect.

## CSS Scope

The generated corpus may keep a dedicated `research-page` scope, but the shell should match the Phase 1 entry pages.

Avoid mixing large design changes with metadata or copy cleanup.

## Deterministic Regeneration

Recommended checks:

- hash all 12 generated outputs before regeneration
- run generator
- record changed outputs
- run generator again
- confirm the second run produces no hash changes
- run static verifier
- run editorial hard-ban scan on generated output and generator source data

## Recommended Implementation Batches

Batch 1: Update generated hub and corpus shell styling only.

Batch 2: Add status labels and canonical consistency. Complete in Phase 8.

Batch 3: Review editorial source data and templates. Complete in Phase 9 as an audit-only source and technical-review pass.

Batch 4A: First controlled editorial implementation batch. Implemented in Phase 10 and awaiting review.

Limits:

- no more than 3 generated routes
- no more than 15 editorial edits
- only high-confidence edits
- no claim expansion
- no new technical claims
- no route changes
- no visual changes
- no PCPI edits
- route-by-route diff review required
- `<main>` hashes expected to change only for approved routes

Recommended first routes:

- `pages/ai-alignment-literature-review.html`
- `pages/ai-alignment-research.html`
- `pages/ai-alignment-executive-summary.html`

Reason:

- clear persistent source locations in `scripts/generate-ai-research-pages.mjs`
- one known hard-ban match in the literature review source
- high reader visibility
- low technical risk if edits are limited to wording cleanup and do not change claims

Batch 4: Regenerate outputs and inspect route-by-route diffs after approved editorial changes.

Batch 4B: Second controlled editorial implementation batch.

Limits:

- no more than 3 additional routes
- no more than 15 edits
- source-level changes only
- route-by-route diff review required
- technical-review items deferred unless separately approved

Recommended candidate routes:

- `pages/ai-alignment-who-this-is-for.html`
- `pages/ai-alignment-methodology.html`
- `pages/ai-alignment-lineage.html`

Reason:

- each route has clear source locations in `scripts/generate-ai-research-pages.mjs`
- likely edits are local sentence-shape cleanup rather than claim changes
- methodology and lineage still require careful status review, so any Batch 4B edits should avoid technical claims

Batch 5: Run hard-ban scanning and technical review.

## Phase 6 Decision

Do not modernize the generated corpus in Phase 6. Keep the hub-only path for the small applied-governance section, and plan a separate generator modernization pass.
